# Engineering conventions

Every feature follows these rules. If a spec needs to break one, it says so explicitly and why.

## Language & style

- TypeScript `strict`, no `any` (use `unknown` + narrowing). ESLint + Prettier, run in CI.
- English identifiers. Domain names follow the [glossary](../01-product/glossary.md) "Code name"
  column (e.g. `Enrollment`, not `Registration`; `ExamRecord`, not `Procesverbal`).
- Files: `kebab-case.ts`; React components `PascalCase` exports; one component per file in `ui/`.
- Comments explain *why*, not *what*. Reference requirement IDs where a rule comes from the source:
  `// SRC-086: remind two weeks before each installment`.

## Module boundaries

- Code lives in `src/modules/<module>/` (see [overview.md](overview.md)).
- Another module may only import from `src/modules/<module>/index.ts`.
- `domain/` has **no I/O** (no Prisma, no fetch) — pure functions and Zod schemas. Business rules
  (eligibility, averages, status transitions) live here and are unit-tested.
- `server/` holds services (`*.service.ts`), read queries (`*.queries.ts`) and server actions
  (`*.actions.ts`). Only `server/` touches Prisma.
- Pages in `src/app/` stay thin: load data via queries, render module UI.

## Server actions & route handlers

Every mutation is a server action built with the shared wrapper:

```ts
export const createFaculty = action({
  permission: "org.faculty.write",
  input: createFacultySchema,           // Zod, from domain/
  handler: async (input, ctx) => {      // ctx: { user, db (transaction), audit }
    return facultyService.create(input, ctx);
  },
});
```

The wrapper: authenticates, checks permission (and scope when a target is resolvable), parses input,
opens a transaction, passes an `audit` helper, maps errors to typed results
`{ ok: true, data } | { ok: false, error: { code, message, fieldErrors? } }`. Never throw raw errors
to the client.

Route handlers (`src/app/api/...`) are used only for: auth callbacks, file downloads, webhooks /
integrations, health checks, job triggers. They use the same `requirePermission` helpers.

## Data & database

- Prisma multi-file schema: `prisma/schema/<module>.prisma`. Model names singular `PascalCase`,
  table names mapped to `snake_case` plural (`@@map("study_programs")`), columns `snake_case`.
- Every model: `id String @id @default(cuid(2))` (or equivalent), `createdAt`, `updatedAt`.
  Business models add `createdById`, `updatedById`.
- **No hard deletes** of business data: use `active=false` / status. Hard delete only for drafts
  and technical rows.
- Money: `Decimal(12,2)`, currency `ALL` unless stated; never floats.
- Dates: store `timestamptz` in UTC; display in `Europe/Tirane`. Pure dates (birth date, due date)
  use `@db.Date`.
- Every migration is generated by `prisma migrate dev`, committed, and must apply cleanly on an
  empty DB and on the previous release's DB.
- Lists that can grow (students, grades, payments) are **paginated server-side**.
- Reference/demo data via `prisma/seed/`; seeds are idempotent.

## Audit

Every create/update/delete/status change of business data writes an `AuditLog` row in the same
transaction via `ctx.audit(...)` (PLT-07). Grade changes, enrollment status changes, payments and
issued documents also require a **reason** field from the user.

## UI

- shadcn/ui components in `src/components/ui`; Tailwind for layout. No other component library.
- Forms: React Hook Form + Zod resolver using the **same schema** as the server action.
- Tables: shared `DataTable` (PLT-10) with server-side pagination, sorting, filters and export.
- All user-visible strings via next-intl (`t("…")`) — no hard-coded copy (ADR-0011).
- Every page works at 360 px width and is keyboard-navigable; form fields have labels; color is
  never the only signal (WCAG 2.1 AA as the target).
- Empty, loading and error states are designed for every list and form.

## Testing

| Layer | Tool | Required for |
|---|---|---|
| Unit | Vitest | every `domain/` rule (eligibility, averages, transitions, fee calc) |
| Integration | Vitest + real Postgres (test DB, reset per file) | every service function and permission rule |
| E2E | Playwright | the main happy path of each user-facing feature, + one permission-denied case |

A feature is **not done** until its acceptance criteria are covered by tests and
`pnpm lint && pnpm typecheck && pnpm test` pass.

## Security checklist (every feature)

- [ ] Every action/route checks permission; list queries use `scopeFilter`.
- [ ] Input validated with Zod on the server.
- [ ] No personal data in logs (log IDs, not names/emails/NIM).
- [ ] File uploads: size limit, MIME allow-list, stored outside the web root, served via
      permission-checked route.
- [ ] Public (no-login) endpoints: rate-limited, CAPTCHA/honeypot, no data echoed back.
- [ ] Audit rows written for business mutations.

## Git

- Branch per feature: `feat/<ID>-<slug>` (e.g. `feat/ORG-02-faculties`).
- Commit messages: `<ID>: <imperative summary>` (e.g. `ORG-02: add faculty CRUD`).
- One feature per PR; the PR updates `FEATURES.md` status and ticks the spec's tasks.
