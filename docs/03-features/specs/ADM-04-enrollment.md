## 1. Context

SRC-020 says a candidate's data are entered once and the Secretariat only confirms them; SRC-032 and
SRC-051 describe registration into a program, cohort and group. ADM-02 stores the application; STU-01
owns the `Person`, `Student`, `Enrollment` and `YearRegistration`. ADM-04 is the bridge: the officer
opens an application, confirms or corrects the personal data, chooses registration type, cohort and
group, and one transaction creates the student records, links them to the application and marks it
`ENROLLED`. Ranking and acceptance (ADM-03) are blocked by Q-13, so until then the Secretariat's
enrollment *is* the final approval (Q-145). Accounts follow from the existing "enrollment opened" hook
(IAM-02); payment plans are generated by Finance (FIN-01); the contract is ADM-05 (Q-147).

## 2. Requirements

### User stories

- As the **Secretariat / Student Affairs officer**, I want to turn an application into a student
  after confirming its data, so that nothing is retyped.
- As the **Secretariat officer**, I want to enroll a list of candidates into one cohort and group at
  once, so that a registration day does not need one form per person.
- As the **Secretariat officer**, I want an applicant who already is a student to get a second
  enrollment, not a duplicate student.

### Acceptance criteria (EARS)

| ID | Criterion |
|---|---|
| AC-1 | THE SYSTEM SHALL grant `adm.application.enroll` to secretary and student-affairs only, and SHALL refuse every enrollment action, and the page `/adm/enrollment`, to other roles. |
| AC-2 | WHEN an officer enrolls an application with the confirmed personal data, registration type, cohort of the applied program, start date and group THE SYSTEM SHALL, in one transaction, create the Person and Student (or reuse the existing student, AC-4), create the Enrollment with its first history row, create the YearRegistration (academic year and year of study taken from the group), set the application to `ENROLLED` with the student, enrollment, time and officer, and audit it with ids only. |
| AC-3 | IF the application is `REJECTED` or `ENROLLED`, does not exist, the cohort does not belong to the applied program, the group does not fit the cohort, or STU-01 refuses the data (national ID or e-mail or NIM conflict, birth date out of range) THEN THE SYSTEM SHALL refuse with a field error and change nothing. |
| AC-4 | IF the person already is a student (same national ID or e-mail) THEN THE SYSTEM SHALL add the enrollment to that student without changing their personal data, and SHALL refuse the registration type "first time" for them. |
| AC-5 | IF a required document of the cycle is missing THEN THE SYSTEM SHALL refuse the enrollment unless the officer ticked "enroll without the missing documents"; the choice SHALL be part of the audit entry. |
| AC-6 | WHEN an enrollment is created THE SYSTEM SHALL run the "enrollment opened" handlers of STU-01 in the same transaction (IAM-02 account access) and SHALL NOT create a payment plan or a contract. |
| AC-7 | WHEN an officer enrolls a selection of up to 100 enrollable applications with one registration type, cohort, start date and group THE SYSTEM SHALL use the personal data as submitted, enroll each candidate independently (a failing candidate is rolled back alone) and report, per candidate, enrolled or the reason it failed. |
| AC-8 | THE SYSTEM SHALL offer `/adm/enrollment`: enrollable applications (status `SUBMITTED`, `IN_REVIEW`, `ACCEPTED`, not yet enrolled) of a chosen program with reference, name, cycle, status and missing documents, and the bulk form. |
| AC-9 | THE SYSTEM SHALL show on the application detail, for an officer with `adm.application.enroll`, the enrollment form prefilled with the application's data while the application is enrollable, and, once enrolled, the link to the student record (for those who may read students) with the enrollment date. |
| AC-10 | THE SYSTEM SHALL keep the application's submitted data unchanged by an enrollment, and SHALL never delete an application. |

### Out of scope

Review, ranking, accept and reject (ADM-03), contract and first invoice (ADM-05), generating the
payment plan (FIN-01), creating the Keycloak account (IAM-02 does it on its own), the entry
qualifications report (STU-05), un-enrolling (STU-02 deregisters), a candidate notification e-mail.

### Assumptions

- Q-145: enrollable statuses `SUBMITTED`, `IN_REVIEW`, `ACCEPTED`; the missing-document override.
- Q-146: the confirmed data become the Person; group gives academic year and year of study; existing student reused.
- Q-147: bulk takes data as submitted, per-candidate result; no plan and no contract here.

## 3. Design

### Data model

`Application` gets the link to the result (the status enum already has `ENROLLED`):

```prisma
model Application {
  // ...
  studentId    String?   @map("student_id")      // -> Student
  enrollmentId String?   @unique @map("enrollment_id")  // -> Enrollment
  enrolledAt   DateTime? @map("enrolled_at") @db.Timestamptz(3)
  enrolledById String?   @map("enrolled_by_id")
}
```

### Permissions

| Permission | Granted to |
|---|---|
| `adm.application.enroll` | secretary, student_affairs |

Reading applications stays `adm.application.read`; the enrollment service uses the STU-01 services
directly inside the action's transaction (their permission is held by the same two roles).

### Server

| Kind | Name | Purpose |
|---|---|---|
| domain | `domain/enroll-rules.ts` | enrollable statuses, `enrollBlocker`, application → personal data mapping |
| domain | `domain/enroll-schemas.ts` | Zod: single and bulk input |
| service | `server/enroll.service.ts` | `enrollApplication`, `enrollMany` (savepoint per candidate) |
| actions | `server/enroll.actions.ts` | `enrollApplicationAction`, `enrollManyAction` (`adm.application.enroll`) |
| queries | `server/enroll.queries.ts` | enrollment draft, enrollable list, cohort and group options |

STU-01 exports `registerStudent`, `addEnrollment`, `registerYear` services from its `index.ts`.

### UI

| Route | Who | What |
|---|---|---|
| `/adm/applications/[id]` | application.read | enrollment form (editable personal data, type, cohort, group, start date) or the result |
| `/adm/enrollment` | application.enroll | program filter, selectable list, bulk form, per-candidate result |

### Edge cases & errors

- Two candidates in a bulk list are the same person: the second is refused `alreadyStudent`/`firstTimeKnown` alone.
- The group's academic year is closed: STU-01's `yearClosed`.
- A second submit of the same application: refused `ENROLLED`.

**Implementation notes:**
- Module `src/modules/adm`: `domain/enroll-rules.ts`, `enroll-schemas.ts`; `server/enroll.service.ts`, `enroll.actions.ts`, `enroll.queries.ts`; `ui/enroll-form.tsx` (`EnrollForm`, `BulkEnroll`); pages `src/app/(app)/adm/enrollment` and the extended application detail.
- STU-01 exports `registerStudent`, `addEnrollment`, `registerYear`, `personalSchema` from its `index.ts`; ADM-04 calls them with the action's `ctx`, so everything is one transaction and one audit trail (`stu.*` entries plus `adm.application.enroll`).
- Bulk: each candidate runs between `SAVEPOINT` and `RELEASE`/`ROLLBACK TO` on the transaction client, so a failure undoes only that candidate (including its audit rows).
- Migration `20261024140000_adm_enrollment` adds the four columns to `applications`.
- The enrollment-opened hook of IAM-02 runs inside each enrollment; no payment plan or contract is created (Q-147).
